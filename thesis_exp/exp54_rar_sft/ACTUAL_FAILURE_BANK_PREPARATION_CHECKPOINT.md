# Exp54 actual failure-bank checkpoint

## Purpose

This stage prepares a neutral inventory of errors actually generated by the
three frozen R3-SFT checkpoints on the 2,654 train rows. It does not decide
whether final preference data will be actual-only, synthetic, or hybrid, and
it does not materialize chosen/rejected pairs.

The severe low-to-high errors involve 53 distinct train records, while severe
high-to-low errors involve 7. Across the three checkpoints, 2,093 of 2,654
records have at least one correct generation. Overestimation errors occur
1,342 times, versus 639 underestimation errors, so the actual failure
inventory confirms that upward score errors are the dominant ordinal failure.

All outputs are parseable and have non-empty rationales. However, 3,613
outputs (45.38%) require deterministic forced completion at the frozen
256-token boundary. Forced completion occurs after the score prefix is
generated, so it does not mechanically change the generated score, but it
does make rationale completeness a required diagnostic in any later
preference-pair eligibility rule. The 894 explicit score-leakage flags are
also retained as diagnostics rather than silently filtered at this stage.

The public aggregate report contains only counts and cryptographic hashes.
Row-level prompts, answers, generated rationales, record IDs, and source
mapping remain private and excluded from version control.

## GPU execution boundary

Execution requires all of the following:

- explicit user confirmation in the current workflow;
- `EXP54_GPU_USER_CONFIRMED=1`;
- `CUDA_VISIBLE_DEVICES` set to exactly one of GPU 4, 6, or 7;
- a read-only check that the selected GPU is idle immediately before launch.

The user explicitly authorized this execution. GPU 4/6/7 were read-only
checked immediately before launch; GPU 5 was occupied and was not used. Three
tmux jobs generated seeds 42/43/44 in parallel. The first launch stopped
before generation because vLLM 0.11 removed the legacy
`prompt_token_ids=` keyword. The runner was changed to the vLLM 0.11 token
prompt contract, covered by a regression test, and all three clean generation
runs then completed.

## ODPO formula check

The original ODPO objective defines the estimated reward as the beta-scaled
policy/reference log ratio and subtracts the preference offset outside that
beta scaling. Therefore, when `Delta` denotes the unscaled
chosen-minus-rejected log-ratio difference, the direct form is:

```text
-log sigmoid(beta * Delta - offset)
```

It is not `-log sigmoid(beta * (Delta - offset))` unless the inside quantity is
defined as `offset / beta`.

Source: Amini, Vieira, and Cotterell, *Direct Preference Optimization with an
Offset*, Findings of ACL 2024, Eq. 7c and Eq. 12:
https://aclanthology.org/2024.findings-acl.592/

## Scientific implication and next decision

This checkpoint answers only which failures the frozen R3 checkpoints actually
produce. It does not yet answer how a preference pair should be built. The
scientific review should now choose among:

1. natural actual-output pairs, which preserve realism but usually vary both
   score and rationale;
2. actual-error-driven field-controlled pairs, which use observed wrong scores
   while holding the rationale fixed;
3. a hybrid in which actual failures are primary and synthetic counterfactuals
   only backfill missing coverage.

Additional stochastic rollout should not be started by default. It should be
considered only if the final pairing policy cannot obtain adequate chosen and
rejected coverage from this greedy inventory, especially for the 76 Label-1/2
train rows.
